## 1. 总体架构

```
┌────────────────────┐    ┌────────────────────┐
│ 用户端 Web (Vue3)   │    │ 管理后台 (Vue3)     │
│ apps/web  :8080    │    │ apps/admin :8081   │
└─────────┬──────────┘    └─────────┬──────────┘
          │ HTTPS / SSE             │
          └──────────┬──────────────┘
                     ▼
             ┌──────────────┐
             │ Nginx (:80/443)│ 静态资源 + 反代 /api → api:9000
             └──────┬───────┘
                    ▼
        ┌────────────────────────┐      ┌───────────────────┐
        │ api  FastAPI (:9000)    │─────▶│ worker  arq        │
        │ REST + SSE + 鉴权限流    │      │ (asyncio 协程并发)  │
        └──┬─────┬─────┬─────────┘      │ 生成/检测/降AI 任务  │
           ▼     ▼     ▼                │ 内置 cron 热点抓取  │
      ┌────────┐┌───────┐┌─────────┐    └────┬──────────────┘
      │MySQL 8 ││Redis 7││Milvus   │         │
      │:3306   ││:6379  ││standalone│◀───────┘
      └────────┘└───────┘└─────────┘
   ── 外部服务 ── DeepSeek API / 智谱 GLM API / 博查搜索 / 阿里云 OSS / 阿里云内容安全
```

**关键决策**
| 决策 | 选择 | 理由 |
|---|---|---|
| 队列 | **ARQ + Redis** | BullMQ 是 Node.js 专属库；Celery 对本项目偏重（同步 prefork 模型、概念/运维负担大），而任务是纯 IO 等待（LLM 流式调用）。ARQ 是 Pydantic 作者写的 asyncio 原生 Redis 队列：单文件配置、内置 cron、与 FastAPI 同一心智模型；规模长大后迁 Celery 成本低 |
| 模型接入 | 统一走 OpenAI 兼容协议 | DeepSeek(api.deepseek.com) 与 GLM(open.bigmodel.cn/api/paas/v4) 都提供兼容接口，一套 SDK 打两家 |
| SSE 推送 | FastAPI StreamingResponse + Redis Pub/Sub | 生成在 worker 执行，api 只做转发，天然支持横向扩容与断线续传 |
| 检测推理 | 独立微服务（FastAPI + ONNX） | CPU 密集的模型推理不能塞进 arq 事件循环；隔离部署，模型升级不重启队列 |
| 向量库 | Milvus standalone | 选题去重、做同款、内容相似；M2 起部署但 M4 才真正使用 |
| 业务库 | MySQL 8（utf8mb4） | 按需选型；JSON 字段用 MySQL JSON 类型 |

## 3. 生成流水线时序（与 04 号文档一致，标注模块归属）

```
POST /api/v1/works/generate
 → [api] 鉴权·限流 → 输入敏感词预检 → 冻结焦耳(joule_freezes) → 建 works → 投递 ARQ 任务
 → [worker·pipelines.single]
    ① prompt_versions 取已发布提示词，装配 system/user
    ② 博查: topic→3 子查询→references(入库 search_references)
    ③ llm_gateway: 按路由调 DeepSeek(主)/GLM(备)，流式
       每 chunk → Redis PUBLISH works:{id} → [api] SSE 转发 delta 事件
    ④ 完成文本 → 阿里云内容安全机审 → 不过则 work.status=banned+退款
    ⑤ AI率检测(启发式+分类器) → ai_rate_checks 入库 → report 事件
    ⑥ 焦耳实扣(两阶段第二段) → done 事件
 失败任意步 → 解冻 → error 事件(含 refunded:true)
```

## 6. SSE 事件协议（对齐 04 号文档设计）

```
event: stage     {"stage":"searching|outlining|writing|detecting","text":"..."}
event: search_end{"references":[{title,url,site_name,summary}]}   # show_references=true 时前端展示
event: delta     {"seq":N,"text":"增量"}        # seq 单调递增，续传从 seq+1 回放(Redis 缓存10min)
event: report    {"ai_rate":18,"level":"human","rewrite_free":true}
event: done      {"work_id":123,"joule_cost":1000}
event: error     {"code":"MODEL_TIMEOUT","refunded":true}
```
实现：worker 产事件 → `Redis PUBLISH works:{id}` + `LPUSH works:{id}:events`（回放用）→ api 订阅转发 `StreamingResponse`。

## 7. ARQ 任务拓扑与幂等扣费

```python
# app/tasks/worker.py —— 队列的全部配置就这一个文件
from arq import cron
from app.tasks.jobs import generate_work, followup, rewrite, de_ai, detect, fetch_hot_topics, aggregate_stats

class WorkerSettings:
    functions = [generate_work, followup, rewrite, de_ai, detect, fetch_hot_topics, aggregate_stats]
    cron_jobs = [
        cron(fetch_hot_topics, minute=0),              # 每小时抓热点
        cron(aggregate_stats, hour=3, minute=0),       # 每日 03:00 聚合模板统计
    ]
    max_jobs = 20          # 单进程 20 个协程并发（IO 密集，等 LLM 流式返回近零成本）
    job_timeout = 300
    max_tries = 2          # 模型侧已有 fallback，队列层只兜基础设施故障
    retry_delay = 5
```

- **投递**：api 侧 `ArqRedis()` 连接池 → `await pool.enqueue_job("generate_work", work_id)`；任务进度不依赖 result backend，直接写 MySQL（works.status）+ Redis 事件流（§6）。
- **两阶段扣费（不变）**：冻结 `UPDATE joule_accounts SET balance-=X, frozen+=X WHERE user_id=? AND balance>=X`（影响行数=0 即余额不足）→ 成功：结算流水；失败/超时：解冻流水。全部以 `idempotency_key=work_id:stage` 防重放（重试时不会重复扣）。
- **CPU 边界**：自训 AI 率分类器推理不放 arq（阻塞事件循环）——单独 detector 微服务（FastAPI + ONNX Runtime，:9100），worker 用 httpx 异步调用；MVP 期也可先用纯启发式打分（无模型）。
- worker 容器横向扩容：直接 `docker compose up --scale worker=3`（多实例消费同一队列，天然分摊）。

| route_key | provider/model | fallback | 用途 |
|---|---|---|---|
| default_chat | deepseek / deepseek-chat | zhipu / glm-4.6 | 常规模板正文 |
| think | deepseek / deepseek-reasoner | zhipu / glm-4.6 | enable_think=true 长文 |
| title_gen | zhipu / glm-4.6 | deepseek-chat | 标题/选题（快） |
| de_ai_rewrite | deepseek / deepseek-chat (T=1.1) | glm-4.6 | 降AI定向重写 |
| embedding | zhipu / embedding-3 | — | Milvus 向量化 |

- 网关统一 OpenAI 兼容 `chat/completions(stream=true)`，负责：多 key 轮换、429 退避、fallback 切换、tokens 计量回写 works（成本核算到模板）。
- **博查**：POST https://api.bochaai.com/v1/web-search `{query, summary:true, count:3}`×3 子查询；Redis 按 topic 哈希缓存 24h。
- **阿里云内容安全**：文本审核 v2（alibabacloud-green SDK）同步调用；verdict=review 进人工队列；输入预检 block 直接拒绝不扣费。
- **OSS**：STS 临时凭证下发给前端直传；桶策略公有读+回调审核图片。
- **Milvus 三集合**（dim=1024，embedding-3）：`topic_vec`（选题去重，cos<0.92 视为重复）、`template_vec`（做同款：用户文案→相似模板召回）、`content_vec`（M4 后：作品查重/洗稿检测）。M2 装好闲置无妨，standalone 空载内存 ~1.5G。

## 10. 安全基线

1. JWT RS256：私钥仅存 api/worker 容器；access 2h + refresh 30d 轮换；
2. 限流：`slowapi`（IP 60/min，generate 10/min/user），兑换接口 5/min + 失败锁定；
3. **提示词永不下发**：detail 接口只回 usage_example/usage_tips（对标焦圈儿做法）；
4. model_providers.api_key 用 AES-GCM 信封加密，密钥来自环境变量；
5. 越权：works 全查询带 user_id 属主条件（统一 repository 层强制）；
6. 管理后台：独立路径 + TOTP 二次验证 + IP 白名单；全部操作进 audit_logs；
7. 注入：SQLAlchemy 参数化 + Pydantic 校验；富文本导出做 XSS 白名单过滤；
8. 隐私：注销即删（保留流水匿名化），日志脱敏手机号/邮箱。

# 核心生成链路详解：模板如何变成一篇文章

> 回答四个问题：① 模板在系统里到底是什么 ② 生成一篇文章的完整过程 ③ 要不要用 LangGraph 这类工作流框架 ④ 用户输入和模板无关时系统怎么办

---

## 1. 模板的本质：一个"配置包"，提示词是它的灵魂

模板 ≠ 一个提示词文件，而是一条**数据库记录**（见架构文档 templates 表），它打包了：

```jsonc
{
  "id": 30, "name": "故事会", "category": "读书",
  // ↓ 灵魂：两个提示词（版本化存储在 prompt_versions 表）
  "system_prompt": "你是一位……（文体人格+结构规范+反AI味约束，约800~2000字）",
  "user_prompt_template": "主题：{topic}\n素材：{material}\n要求字数：{length}",
  // ↓ 引擎配置
  "model_route": "default_chat",        // 用哪个模型（deepseek-chat）
  "temperature": 0.95,                   // 创意类温度调高
  "enable_web_search": true,             // 生成前是否联网搜资料
  "enable_think": true,                  // 是否用推理模型（R1类）
  "output_format": "标题+导语+3~5个小节+金句结尾",
  // ↓ 商业与运营
  "joule_price": 1000, "usage_example": "…", "usage_tips": "…"
}
```

**所以"每个模板都有一个提示词吗？"——是的，而且有两个**：system_prompt（定义"我是谁、怎么写"）和 user_prompt_template（定义"用户输入怎么装配"）。焦圈儿 55 个模板的本质差异就是这 55 套 system_prompt。模型层是共用的（大多 deepseek），**提示词才是产品资产**——这也是焦圈儿把"提示词权限/复刻提示词"做成付费点的原因。

## 2. 一篇文章的诞生：完整时序（9 步）

```
用户: 选模板30"故事会" + 输入"写瑞幸联名茅台的营销分析"
 │
 ├─① 前端表单校验: topic 必填、长度、(槽位化模板的必填槽位)
 ├─② POST /works/generate → 后端: 输入敏感词预检(不过→拒绝,不扣费)
 ├─③ 冻结焦耳 1000J (两阶段扣费第一阶段)
 ├─④ 创建 works 记录(status=generating), 任务入队 BullMQ
 │
 ├─⑤ Worker 取任务, 装配最终提示词:
 │     system = prompt_versions.system_prompt (模板的)
 │     user   = user_prompt_template 渲染 {topic, material, length}
 │
 ├─⑥ [enable_web_search=true] 调博查:
 │     topic → 拆3个子查询 → 拿回9条 references
 │     → 拼进 user prompt: "参考资料:\n[1]标题—摘要…\n[2]…"
 │     → (这就是最简版 RAG; 深度版做embedding筛选)
 │
 ├─⑦ 调 LLM 流式生成 (OpenAI兼容接口, stream=true)
 │     每 chunk → SSE event: delta → 客户端逐字显示
 │     ⚠️ 焦圈儿的"构思大纲/初稿/润色/验收"阶段文案,
 │        实测是同一毫秒批量推送的进度条标签(见调研报告2.6),
 │        ≠ 每个阶段真有一次LLM调用!
 │
 ├─⑧ 后处理流水线:
 │     a. 内容机审(阿里云/易盾) → 不通过则拦截
 │     b. AI率检测(启发式+自训分类器) → ai_rate=15% 人工特征
 │        ├─ 达标 → 生成检测报告
 │        └─ ≥80% → 自动走"降AI重写"节点或提示免费重写
 │     c. 排版转换: Markdown → 公众号富文本(规则引擎,非LLM)
 │
 └─⑨ 落库(status=done) + 焦耳实扣(失败则解冻) + SSE done 事件
```

**关键认知：90% 的场景是"一次 LLM 调用"完成的**。所谓"逻辑构建、金句打磨、风格润色"这些动作，全部被压缩在那一份 2000 字的 system_prompt 里（"写作前先在内心构思三段式叙事线，输出时直接成文"），而不是真的分四次调用四次模型。焦圈儿的 SSE 协议里那些阶段文案就是证据。**这是成本和时延的最优解：一篇 2000 字只要一次调用、60~90 秒出全文。**

## 3. 那什么时候才需要真·工作流（LangGraph）？

| 场景 | 模式 | 说明 |
|---|---|---|
| 常规模板（故事会/科技吐槽/小红书） | **单次调用** | system_prompt 内含分步指令，一次流式出全文 |
| 超长深度报道（5000字+引用） | **多步管道** | 大纲→搜索→分节生成→汇总，每节一次调用（上下文窗口限制） |
| 降AI率 Agent | **检测-重写循环** | 检测→定位高风险段落→定向重写→复检→循环(≤3次)，天然是图 |
| 今日选题 | **单次调用** | 关键词→10个标题，最简单 |
| 智能排版发布 | **纯规则** | 不用 LLM |

**模板路由到工作流的机制**：templates 表加一个字段 `workflow_type`（single / deep_report / de_ai_loop / topic），Worker 里就是一个映射：

```ts
const pipelines = {
  single:      singleShotPipeline,     // 一次调用,占比90%
  deep_report: outlineThenWritePipeline, // 大纲→分节
  de_ai_loop:  detectRewriteLoopPipeline, // 检测重写循环
  topic:       titleGenPipeline,
};
await pipelines[template.workflow_type](ctx);
```

**要不要 LangGraph？** 我的建议：**MVP 不要**。理由：
1. 你的流程是"线性管道 + 少量条件分支"，用 async 函数链 + switch 就能写清楚，调试直接看日志栈；
2. LangGraph 的价值在复杂状态机：多 agent 协作、人工介入节点、状态回溯、并行分支汇聚——你二期之前用不上；
3. 多一层框架 = 多一层抽象成本 + 出问题更难排查。
**什么时候换 LangGraph**：当你出现"3 个以上 agent 角色互相对话"或"用户在流程中间要审批修改"这类需求时。届时把 pipeline 函数迁移成 Graph 节点成本很低（因为你的每一步已经是纯函数式的 `ctx → ctx`）。

## 4. 灵魂问题：用户输入和模板"毫无关联"怎么办？

### 4.1 先破题：多数"无关"是伪命题——模板管"怎么写"，用户管"写什么"

模板定义的四个维度全部属于**形式层**：文风（吐槽/深情/研报腔）、结构（总分总/故事线/清单体）、视角（第一人称老友/第三方观察者）、节奏（长短句/口语密度）。主题层完全开放。

所以「输入"人工智能行业分析" + 选"情感夜话"模板」→ 系统产出一篇**用情感叙事写的 AI 行业稿**（例：从"一个42岁程序员被AI替代那天"的故事切入行业分析）。这**不是 bug，是 by design**——"硬写成模板格式"正是用户要的效果：**格式服从模板，主题服从用户**。

甚至焦圈儿的"科技吐槽官"模板写情感主题、写美食主题，会产出很妙的跨界文——这是模板玩法的一部分。

### 4.2 真正的冲突有三种，处理策略各不同

**冲突 A：模板有强主题约束（影评/论文降重/降AI率）**
这类模板的输入不是 topic 而是"结构化素材"（影评必填影片名、降AI率必贴原文）。处理：**槽位化表单**——前端按模板渲染不同输入表单，必填槽位缺失直接拦截提交，根本到不了 LLM。降AI率模板收到一篇正常文也会正常工作（检测→改写），不存在冲突。

**冲突 B：软性不匹配（写"宠物殡葬"选了"军事"模板）**
模型会自动调和：文风用军事的（硬朗、排比、"阵地/攻防"类比），主题仍是宠物殡葬。产出成立但可能怪。产品策略二选一：
- 焦圈儿做法：完全放行，用户自己负责（自由度最大）；
- 我们可差异化：**匹配度预检**——用 embedding 算"topic 与模板主题倾向的余弦相似度"（成本≈0.0001元），低于阈值给一行提示"该模板更适合科技类主题，推荐换用【XX】模板"，用户可一键切换或忽略。这是体验加分项，放二期。

**冲突 C：输入无法成文（乱码/"哈哈"/纯表情/空主题）**
前置规则拦截（长度<5字、重复字符检测）+ 首次输出的合规校验（LLM 返回"无法理解主题"标记→引导补充输入，**不扣费**）。这是必须做的，否则用户浪费焦耳会产生客诉。

### 4.3 把"调和规则"写进 system_prompt（兜底指令）

每个模板的 system_prompt 末尾都有一段**优先级声明**，这是解决一切不匹配的总开关：

```
【输入处理规则】
1. 用户主题永远优先：无论主题与本模板的典型场景是否相关，
   都必须围绕用户给定主题创作，禁止要求用户换主题或泛泛而谈。
2. 本模板的文风、结构、视角规范无条件适用于任何主题。
3. 若主题信息量过少（<10字且无具体对象），在文中以设问自然带出，
   不要在正文里向用户提问。
4. 用户提供的素材/原文中的事实优先于你的常识；联网资料仅作背景。
```

## 5. 端到端示例：亲手走一遍

**用户**：选"故事会"模板，输入"写瑞幸×茅台联名的营销分析，2000字"

**装配后的最终请求**（截取关键部分）：

```text
[system]
你是一位有12年副刊经验的故事型主笔，笔名"老周"。
你的文风：像和读者在深夜大排档聊天；段落长短错落（3~9句）；
口头语配额：每500字允许≤3次"说白了/讲真"；
禁止：首先/其次/总之/赋能/抓手；禁止总分总开头；
结构：场景切入→冲突→转折→留白结尾；金句不加粗不喊口号。
【输入处理规则】（见4.3）
【输出格式】标题(≤20字)+导语(80字)+正文3~4节(小标题口语化)+结尾(≤100字)

[user]
主题：写瑞幸×茅台联名的营销分析
素材：（用户未填）
字数：2000字
参考资料：
[1]瑞幸茅台联名首日销量破545万杯—…
[2]酱香拿铁刷屏背后的情绪营销—…
```

**输出**（模型一次流式产出）：标题《一杯酱香拿铁，把年轻人和茅台都灌醉了》→ 导语从"早八点的写字楼电梯"场景切入→ 三节：'这杯酒为什么是现在'/'刷屏的不是咖啡是话题'/'茅台图什么'→ 留白结尾。

**后处理**：机审通过 → AI率检测 12%（人工特征）→ 排版转公众号富文本 → 扣 1000J → done。

## 6. 给你的实现顺序（核心逻辑开发 5 步）

1. **先跑通"裸链路"**（1天）：hardcode 一个模板的 system_prompt + topic → 调 DeepSeek 流式接口 → SSE 打到页面。能逐字出文就赢了一半；
2. **模板表+装配器**（2天）：prompt_versions 两张表 + 渲染 user_prompt_template（简单的字符串替换即可）；
3. **加搜索注入**（1天）：博查 API → references 拼进 prompt；
4. **加检测与计费**（3天）：启发式 AI 率打分 + 焦耳冻结/扣减/退款；
5. **再加第二个 workflow_type**（降AI率循环）——这时你会自然发现"要不要框架"的答案（通常是不用）。

## 附录 A：实测验证（2026-10-11，焦圈儿官网）

### A.1 生成接口本体（此前未知的最后一块拼图）

```
POST https://api-server.jiaoquaner.com/api/v1/ai/chat
{"content_id":null,          // 本轮归属的作品；null=新作品
 "parent_content_id":null,    // 追问树的父节点（追问时指向上一轮）
 "turn":1,                    // 对话轮次（追问=+1）
 "input":"讲一讲自媒体IP的商业化历程",
 "template_id":"74",
 "response_length":1,         // 篇幅枚举（推测 1/2/3=短/中/长）
 "enable_think":true,
 "enable_web_search":false,
 "client":"web"}              // 端标识：web/ios/android（埋点与计费归因）
```

→ **设计启示**：焦圈儿把"每次生成"建模为**绑定模板的对话轮**（chat-turn）。我们的 works + work_segments 表正是这个模型：首轮 content_id=null 建 work，追问同 work 内 turn+1、parent 指向父段落，天然形成追问树。response_length、client 两个参数应补进我们的 API 设计。

### A.2 重大发现：enable_web_search=false，但搜索依然执行了

请求里开关是 false，SSE 里 search_start/search_end 照常触发（博查、按主题拆 3 个子查询）。且最终成文**没有引用标注**。结论：

> **联网搜索是服务端流水线的默认动作（至少 enable_think=true 时），开关控制的很可能只是"引用是否在成文中展示"，而不是"是否搜索"。** 搜索子查询由用户主题生成（与模板无关），作为背景资料喂给思考模型，起到防瞎编的 grounding 作用。

→ 我们的设计应对：搜索步骤常开（成本低、防幻觉），flag 改名为 `show_references` 更诚实。

### A.3 SSE 协议精读（含时间戳分析）

```
content_block_start(index=0) → thinking block
  ├─ 045294(+6.8s) 构思与大纲规划      ← 真实间隔：此刻思考模型调用开始
  ├─ 047899(+2.6s) 正在分析相关题材     ← 思考调用仍在进行
  ├─ 047900 × 8条阶段标签批量推送       ← 装饰性进度叙事
  └─ content_block_stop(index=0)
content_block_start(index=1, text) → 正文流
  └─ text_delta：1~4字/包（服务端重切块，打字机效果）
```

- 真实耗时在 search_end(038461) → text_start(047899) 之间约 **9.4 秒** = DeepSeek 思考模型的真实推理时间；
- 10 条"阶段文案"里只有前 2 条有真实时间差，后 8 条同一毫秒推完——**进度叙事与真实执行的对应关系至此完全实锤**；
- 协议完全模仿 Anthropic Messages 流式（content_block_start/delta/stop + index 多块结构）。

### A.4 模板-主题错配实测（用户问：主题与模板无关怎么办）

**输入**：主题"自媒体IP的商业化历程" × 模板74"吃喝指南"（美食类，人设"组团盲测、替你踩雷种草的硬核吃货"，deepseek+think，500J）

**结果**：主题 100% 被尊重——全文零美食内容，完整讲商业化四阶段；但模板的**人格与语感全面渗透**：

| 输出原文 | 渗透来源 |
|---|---|
| "但有一说一，这套模型看着热闹，也挺容易**噎住**" | 吃喝语汇 |
| "广告仍然能赚，但不再是唯一**一道菜**" | 吃喝语汇 |
| "流量像**自来水**，来得便宜" | 生活化比喻（吃货博主风格） |
| "翻译一下：…"、"但有一说一" | 唠嗑体口头禅（种草博主人格） |
| 短句成段、设问推进、结尾"数字不动产"金句 | 公众号美食爆文的结构基因 |

**结论（实锤第 4 章的推断）**：系统不做任何"匹配度拦截"，靠 system_prompt 中的优先级声明完成调和——**主题完全服从用户，人格/语气/比喻库/结构完全服从模板**。错配的产物是"用吃喝博主口吻写的商业评论"，成立且可读，甚至有记忆点。这就是模板化写作的设计哲学。
